# Issue #18 上部にヘッダー分のマージンがない

## 背景・目的

Issue 本文: 「コンテンツが上にズレてるので、ヘッダー部分のボタンとかに重なり、操作できない」。
画面上部の内容がステータスバー／ナビゲーションヘッダー（例: 記録一覧の「追加」ボタン）に重なり、タップできない。上端の安全領域（セーフエリア）とヘッダー分の余白を正しく確保し、すべての画面で上部の操作が可能な状態にする。

現状（調査結果）:
- `src/app/_layout.tsx` のルート `Stack` は既定で `headerShown: false`。`(tabs)` は `Tabs` 自身のヘッダー、`record/*` `records/[id]` は Stack のヘッダー（`headerShown: true`）を使う。
- アプリ内に `react-native-safe-area-context`（`SafeAreaView` / `useSafeAreaInsets`）の利用はなく、画面コンポーネントは上端インセットを一切考慮していない。ヘッダーが描画される画面ではヘッダーがインセットを処理するが、ヘッダーが描画されない・インセットが 0 になる状況（Android のエッジ・ツー・エッジ、ヘッダー非表示のルート、全画面表示のバーコード読み取り画面など）で上端に重なる。
- 実機が無く開発サーバーも起動できないため、原因となる画面・端末の特定は実装工程でコードとテストから行う（判断ログ参照）。

## スコープ

### やること
- すべての画面（記録一覧・分析・記録の追加／編集／詳細・ISBN で探す・バーコード読み取り）で、上端のセーフエリア分の余白を確保し、ヘッダー・ステータスバーとコンテンツが重ならないようにする。
- ヘッダーが表示される画面で余白が二重にならないようにする（ヘッダーが処理済みの上端インセットを画面側で重ねて足さない）。
- 上端余白の振る舞いを検証するテストを追加する。

### やらないこと
- ヘッダーのデザイン変更、文言変更、ナビゲーション構成の変更
- 下端（タブバー／ホームインジケーター）の余白調整（問題が上端に限られるため。ただしバーコード画面で重なる場合のみ同画面で対応可）
- 新しいライブラリの追加（`react-native-safe-area-context` は導入済み。依存追加なし）

## 受け入れ条件

- [ ] 上端インセットが 0 でない環境（テストでは `SafeAreaProvider` の `initialMetrics` で top=47 などを与える）で、ヘッダーが表示されない画面（バーコード読み取り画面の権限要求・カメラ表示、およびルートでヘッダーなしのまま描画される画面）の内容が上端インセット以上の位置（`paddingTop` / `marginTop` ≥ top）から始まる
- [ ] ヘッダー付きの画面（記録一覧タブ、記録の追加・編集・詳細、ISBN で探す）で、画面コンテンツ側が上端インセットを重複して足していない（コンテンツ先頭の上余白がインセット分増えない）
- [ ] 記録一覧タブのヘッダー右「追加」ボタンが、コンテンツと重ならずタップでき、押すと `/record/new` に遷移する（既存テストが維持される）
- [ ] 上端インセット 0 の環境（既定のテスト環境）で既存の表示・レイアウトが変わらない（既存テストがすべて通る）
- [ ] `pnpm check` が通る（カバレッジ閾値・差分カバレッジを満たす）

## 画面・振る舞い

- 画面種別ごとの上端処理:
  - ナビゲーションヘッダーあり（Tabs / Stack のヘッダー）: ヘッダーがステータスバー分を含めて高さを確保する。画面コンテンツは追加の上端インセットを持たない。
  - ヘッダーなし／全画面（バーコード読み取りのカメラ表示など）: 画面コンテンツ側で `useSafeAreaInsets().top` 分の余白を確保し、上部の操作要素（戻る・閉じる・案内文）が重ならない。
- エラー時の振る舞い: なし（レイアウトのみの変更）。

## 設計

変更するファイル（実装担当向け）:
1. 原因の特定: `src/app/_layout.tsx` と `src/app/(tabs)/_layout.tsx`、`BarcodeScanScreen.tsx` の描画構造を確認し、どの画面で上端インセットが未処理かをテストで再現する（`SafeAreaProvider initialMetrics` を与えた `renderRouter` / `render`）。先に失敗するテストを書くこと。
2. ルート: `src/app/_layout.tsx` で `SafeAreaProvider` が確実にツリー上位にあることを確認（expo-router が提供する場合は追加しない。不足するならルートに明示的に追加）。`StatusBar` は現状維持（`style="auto"`）。
3. 共通コンポーネント `src/components/ScreenContainer.tsx`（新規）: ヘッダーなし画面用。`useSafeAreaInsets()` の `top` を `paddingTop` に適用し、`backgroundColor: colors.background`、`flex: 1` を持つ。ヘッダーあり画面には使わない。`SafeAreaView`（`react-native-safe-area-context` 製、`edges={['top']}`）で実装してもよい。
4. ヘッダーなしで描画される画面（バーコード読み取りなど、調査で特定したもの）を `ScreenContainer` で包む、またはルートの `Stack.Screen` を `headerShown: true` にしてヘッダー側に処理を任せる（後者のほうが二重余白を避けやすいので優先して検討する）。
5. 色・余白は `src/theme.ts` の既存定数を使う（新しい定数が必要なら追加）。

状態管理・データ構造の変更なし。依存追加なし。

## 判断ログ

- **原因の扱い**: Issue は症状のみで、対象画面・端末が不明。ただし質問しても手戻りは小さい（上端処理の方針はどの画面でも同じ）ので、`needs_clarification` にせず「全画面で上端を安全にする」方針で進める。実装時にテストで再現できなかった画面は、変更せず PR の判断ログに「再現せず」と記録する。
- **案 A（採用）**: ヘッダーがある画面はヘッダーに任せ、ヘッダーのない画面だけ `ScreenContainer` で上端インセットを確保する。理由: 二重余白を避けられ、変更範囲が最小。
- **案 B（却下）**: すべての画面を一律 `SafeAreaView` で包む。ヘッダーがある画面で余白が二重になるため。
- **案 C（却下）**: 各画面に固定の `paddingTop`（例: 44）を足す。端末ごとにインセットが異なり（ノッチ／パンチホール／Android）、再発するため。
- **新規ライブラリなし**: `react-native-safe-area-context` が導入済みのため追加不要。
- **自動テストの限界**: 実機描画は確認できないため、インセットの適用はスタイル値の検証にとどめる。
